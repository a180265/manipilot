# 统一校准与输入法点击验收实施方案

状态：校准算法与流程背景文档。原多设备冻结规范已改为
[历史规范导航](摄像头辅助程序多设备调试台实施冻结规范.md)，不再是现行唯一依据。
涉及多摄像头、设备上下文、绑定身份、档案版本、阈值与接口时，以当前源码、
[公开契约](../api/contracts/README.md)及[验收总表](实施目标与验收总表.md)的对应证据为准。

> **当前规则（2026-09-14）**：机械臂校准的 E 阶段只有两项：`ime_input_tap`（下发一次固定文字并点击候选完成输入）和 `ime_delete_clear`（删除键清空）。不是两次文字输入，也不包含微信测试会话。历史 `acceptance.wechat` 不得阻断 `ready` 或通用发送门禁；微信真实发送必须由 WX 在每次任务中核对目标、账号/会话、正文哈希和发送后效果证据。

2026-09-28 校准页生命周期与动作前检查补充：

- 手机仅在校准页处于前台、窗口有焦点且布局完成时上报 `open`；失焦或暂停
  立即清除本地布防并串行上报 `closed`，不因此取消服务端校准会话。
- 手机轮询等待后、机械动作前，再核对原手机会话、活动页面、样本编号与序号、
  daemon 会话、绑定、急停及自动运行取消状态；发生变化则本次不动作。
- `POST /api/v1/calibrations/{sessionId}/disarm` 向后兼容增加可选正整数
  `sequence`。传入时在服务端锁内同时比较 `sampleId` 和 `sequence`；
  不匹配返回 409 `sample_not_armed`，保留新的布防。省略时保留旧接口语义。
  向导触点等待的异常及超时清理传入原序号；服务端与调试台须配套加载。
- ADB 启动回执不证明页面在前台，现场还须核对手机截图与摄像头画面。

## 1. 目标与范围

本方案把电机调试台、Android K40 输入法校准页和摄像头定位串成一套可恢复、可检查、可拒绝执行的流程；微信业务验收由 WX 独立负责。

完成后，`arm-01` 应能够在当前固定安装状态下：

- 以可靠的 Z 悬停高度和点击参数执行普通点击；
- 以可调节的长按时长触发输入法“删除全部内容”；
- 将机械臂 XY 坐标换算成手机屏幕坐标；
- 将摄像头识别出的屏幕文字、文字按钮、App 图标及其下方名称换算成点击位置；
- 点击输入法候选/输入位置、删除图标、微信发送按钮和已登记的微信界面目标；
- 在执行前检查屏幕边缘、屏幕方向、分辨率、daemon 会话和校准版本；
- 检查失败时拒绝自动任务，不使用旧坐标或默认坐标继续操作。

第一版不处理“没有文字、没有登记、也没有稳定模板”的任意纯图标。

## 2. 已确认的现场约束

1. 摄像头绝对固定，不把摄像头移动作为日常检测项。
2. 手机由人工固定；手机固定后由人工打开输入法 App 的“屏幕校准”功能。
3. 输入法校准页使用现有 K40 `CalibrationActivity`，调试台负责创建会话、布防采样和接收触点回报。
4. 普通点击和长按清除均复用调试台现有 `TAP` 动作。
5. 调试台已有下压深度、下压速度和接触停留时间参数。
6. XY 最低需要 3 个不共线点，实际流程默认采集 5 个点。
7. 视觉校准目标由系统分布，用户通过点动机械臂把探头调整到目标落点并确认。
8. 视觉校准完成后必须在调试台内完成两项输入法验收；不要求进入测试微信。
9. 除页面内部业务内容变化外，屏幕边缘变化、手机重新摆放、控制器会话变化、屏幕方向或分辨率变化均要求重新校准。

## 4. 输入法校准入口

### 4.1 当前实际入口

原始 Android App 的入口是：

```text
K40 输入法 App 主页面
→ 点击“屏幕校准”
→ CalibrationActivity
```

对应源码：

- `/Users/ye/Desktop/AI_demo_更新/K40InputMethod/app/src/main/java/com/example/k40ime/MainActivity.kt`
- `/Users/ye/Desktop/AI_demo_更新/K40InputMethod/app/src/main/java/com/example/k40ime/CalibrationActivity.kt`

`CalibrationActivity` 当前在 Android Manifest 中为 `exported=false`，因此第一版不要求调试台远程拉起手机页面。现场流程固定为：

```text
人工固定手机
→ 人工打开 K40 输入法 App
→ 人工点击“屏幕校准”
→ 调试台创建/等待校准会话
```

页面打开后会轮询：

```text
GET /api/v1/devices/{deviceId}/calibration
```

看到活动会话后，页面自动回报：

```text
POST /api/v1/calibrations/{sessionId}/client
{ "deviceId": "...", "state": "open" }
```

调试台退出向导时调用：

```text
POST /api/v1/calibrations/{sessionId}/complete
```

或在取消时调用：

```text
POST /api/v1/calibrations/{sessionId}/cancel
```

## 5. 总体状态机

统一校准流程使用以下状态：

```text
IDLE
  → PRECHECK
  → PHONE_CALIBRATION_OPEN
  → Z_READY
  → XY_CALIBRATING
  → SCREEN_GEOMETRY_CALIBRATING
  → TARGET_CALIBRATING
  → DEBUG_ACCEPTANCE
  → READY
```

`DEBUG_ACCEPTANCE` 只包含输入法文字/候选点击与删除清空两项。旧 `WECHAT_ACCEPTANCE`
状态仅用于兼容历史记录，不是当前流程阶段，不要求打开微信测试会话。

任一阶段发生下列情况，进入 `INVALIDATED`：

- daemon session 改变；
- 手机屏幕边缘检测不匹配；
- 屏幕方向改变；
- 屏幕分辨率或有效视口改变；
- 校准档案版本不完整；
- 拟合残差超过阈值；
- 点击回报与当前布防点不匹配；
- 调试台、摄像头桥或输入法服务不可用。

`INVALIDATED` 只允许查看原因、重新开始校准或人工取消，不允许自动点击。

## 6. 第一阶段：Z 轴和点击参数校准

### 6.1 进入条件

- daemon 已连接；
- 当前 session 已生成；
- 调试台取得 debug 运动租约；
- 急停未锁定；
- 手机已人工固定；
- K40 App 已人工进入“屏幕校准”页面；
- 校准会话状态为 `clientState=open`。

### 6.2 标定悬停高度

页面增加按钮：`标定 Z 轴高度`。

操作步骤：

1. 用户使用 Z 点动把探头移动到屏幕上方安全悬停位置。
2. 用户确认探头没有接触屏幕。
3. 点击 `标定 Z 轴高度`。
4. 调试台读取当前 `MPos.z`。
5. 将该数值保存为当前设备的 `hoverZ`。
6. 显示“悬停高度已保存：Z = ... mm”。

保存前必须记录：

- daemon session；
- 设备编号；
- 当前 MPos；
- 操作者确认时间；
- 摄像头当前帧序号；
- 屏幕边缘快照摘要。

`hoverZ` 是当前 daemon 会话坐标系下的绝对位置。daemon 重连后旧 `hoverZ` 不能直接用于业务，必须重新确认。

### 6.3 测试普通点击

用户点击 `测试点击` 后，调试台执行：

```text
TAP tapDepth FtapFeed PtapDwellSec
```

现有实现已经满足：

- 下压距离可调；
- 下压速度可调；
- 接触停留时间可调；
- TAP 完成后自动回到点击前 Z 位置。

调试台同时创建一个校准布防点，等待输入法页面回报触点。页面需要显示：

- `等待点击回报`；
- `已收到点击回报`；
- 回报序号；
- 回报屏幕坐标；
- 本次点击深度；
- 下压速度；
- 接触停留时间；
- 是否为短按或长按测试。

输入法校准页本身没有视觉点击反馈，因此本阶段不依赖摄像头画面判断点击是否成功。成功条件是：

```text
机械动作完成
且输入法校准页收到合法 ACTION_UP
且服务端收到匹配的 sampleId + sequence
```

用户点击 `合理并保存点击参数` 后保存普通点击参数。用户点击 `不合理，继续调整` 后保留本次记录但不覆盖正式参数。

连续成功 3 次作为推荐验收，不作为硬门槛；一次合法触点回报即可允许保存。

### 6.4 普通点击参数

```json
{
  "hoverZ": 2.0,
  "tapDepth": 3.0,
  "tapFeed": 1500.0,
  "tapDwellMs": 0,
  "tapDwellSec": 0.0
}
```

实际保存时只保留一个停留单位，建议内部统一使用毫秒，发送 daemon 指令时转换为秒，避免页面和档案同时保存两种可冲突数值。

当前 `/Users/ye/Desktop/WX/arm_fleet/scripts/motor_debug_server.py` 已经把 `dwell` 转换为 daemon 的 `P<sec>` 参数，`/Users/ye/Desktop/WX/arm_fleet/scripts/arm_daemon3.py` 已经把它转换为 `G4 P<sec>`。因此点击动作本身直接复用，改造重点是向导状态、参数保存和回报监听。当前页面输入框的最大值是 2 秒，若现场需要更长停留，只需扩大页面范围并在服务端增加统一上限，不需要改写 TAP 动作。

### 6.5 长按清除参数

长按清除使用同一 `TAP` 接口，但使用独立参数：

```json
{
  "deleteHoldMs": 2000,
  "deleteDepth": 3.0,
  "deleteFeed": 1500.0
}
```

默认 `deleteHoldMs=2000`，允许现场调整，例如 1800~3000ms。调试台发出的动作是：

```text
TAP deleteDepth FdeleteFeed P(deleteHoldMs / 1000)
```

当前 K40 输入法的长按逻辑在约 2000ms 后调用清空全部内容：

`/Users/ye/Desktop/AI_demo_更新/K40InputMethod/app/src/main/java/com/example/k40ime/K40InputMethodService.kt`

因此保存规则必须满足：

- 机械停留时间不能短于输入法阈值；
- 推荐在阈值上留出 100~300ms 裕量；
- 如果将来要调整输入法自身阈值，必须同步修改输入法设置与校准档案；
- 长按清除不能复用普通点击的 `tapDwellMs`。

这里要区分两个可调时间：

```text
机械停留时间：调试台通过 TAP 的 P 参数控制，可以现场调节；
输入法触发阈值：当前 K40 代码中的 DELETE_CLEAR_THRESHOLD_MS，默认 2000ms。
```

第一版只调机械停留时间即可。若测试发现输入法阈值本身需要改，再把该阈值做成输入法设置项或随设备配置下发，不能只修改机械臂参数后假设输入法阈值也改变。

### 6.6 Z 阶段验收标准

- `hoverZ` 已保存；
- 普通点击至少 1 次收到合法回报；
- 推荐 3 次连续回报成功；
- `tapDepth`、`tapFeed`、`tapDwellMs` 已保存；
- 长按清除参数已保存或明确标记为待验收；
- Z 轴参数与当前 daemon session 绑定；
- 任意参数变更后，旧 Z 验收状态变为待确认。

## 7. 第二阶段：XY 与手机屏幕关系校准

### 7.1 采样点设计

最低 3 个不共线点才能拟合二维仿射关系。默认使用 5 个系统分布点：

1. 中心；
2. 左上安全区；
3. 右上安全区；
4. 左下安全区；
5. 右下安全区。

安全区应避开系统状态栏、导航栏、屏幕圆角和输入法页面退出按钮。

系统只负责给出目标分布和编号；用户负责通过摄像头和点动按钮把机械探头手动调到目标位置。

### 7.2 每个 XY 点的操作

每个点执行以下子流程：

1. 调试台显示当前目标编号及归一化位置。
2. 手机输入法校准页显示对应目标区域。
3. 用户通过摄像头观察探头，使用 XY 点动修正探头落点。
4. 点击 `准备本点`。
5. 调试台读取当前 `MPos.x/y`。
6. 布防 `sampleId + sequence`。
7. 调用现有 `TAP` 执行一次普通点击。
8. 输入法页回报实际触点像素。
9. 调试台显示目标位置、实际回报位置和误差。
10. 用户点击 `接受此点`，保存配对样本。

如果落点不理想，用户点击 `继续修正`，该次记录保留在试验记录中，但不进入正式拟合样本。

### 7.3 拟合关系

统一使用：

```text
screenX = a * robotX + b * robotY + c
screenY = d * robotX + e * robotY + f
```

推荐使用 5 个正式点拟合，至少满足：

- 点数不少于 3；
- 机械坐标不共线；
- 手机回报屏幕尺寸和方向一致；
- RMS 残差不超过 3px；
- 单点最大残差建议不超过 6px。

拟合后保存正向和逆向计算所需参数，但不保存任何未经拟合验证的临时坐标。

手机端的标靶绘制、触点回报和 `screenWidth/screenHeight` 必须使用同一个
校准页根视图坐标系。Android 使用 `MotionEvent.x/y`，不使用包含状态栏、
导航栏或异形屏偏移的 `rawX/rawY`。否则即使拟合残差很小，也会把
系统窗口偏移错误吸收进 XY 映射。

### 7.4 XY 阶段验收

拟合完成后增加 3 个不参与拟合的验证点：

- 屏幕内上方偏左；
- 屏幕内下方偏右；
- 中心偏移位置。

每个验证点执行一次机械点击，由输入法回报实际坐标。验证结果只用于验收，不修改拟合参数。若误差超限，回到 XY 校准阶段。

## 8. 第三阶段：摄像头与屏幕内容关系校准

### 8.1 屏幕边缘作为稳定性基准

摄像头固定，因此运行时不检查摄像头是否移动；运行时检查摄像头画面中的屏幕边缘是否仍与校准时一致。

屏幕基准数据应包括：

- 屏幕四边线段；
- 四角位置；
- 屏幕宽高比；
- 可视区域内缩边界；
- 屏幕方向；
- 屏幕有效尺寸；
- 亮度/清晰度最低要求。

推荐使用屏幕边框几何，不要求把手机外壳识别成独立物体。

### 8.2 目标分布

手机校准页面显示 5 个已知目标，系统自动分布在：

- 左上；
- 右上；
- 中心；
- 左下；
- 右下。

每个目标包含：

- 目标编号；
- 屏幕像素中心；
- 目标矩形；
- 目标类型；
- 目标安全点击区域。

### 8.3 用户手动校准落点

每个目标的流程：

1. 摄像头识别目标中心或目标矩形。
2. 系统根据已有 XY 映射估算机械臂坐标。
3. 机械臂回到 `hoverZ` 并移动到估算位置。
4. 用户通过点动按钮修正探头位置。
5. 点击 `测试目标`。
6. 机械臂执行一次普通 TAP。
7. 输入法校准页回报触点。
8. 调试台计算“视觉预测点”和“实际触点”的误差。
9. 用户点击 `接受此点` 保存最终校准点。

这一阶段同时验证：

- 摄像头像素识别是否正确；
- 摄像头画面到屏幕像素的关系是否正确；
- 屏幕像素到机械 XY 的关系是否正确；
- Z 点击是否能够触发输入法页面；
- 点击偏差是否在可接受范围内。

### 8.4 视觉映射

校准数据分为两层：

```text
cameraPixel → screenPixel
screenPixel → robotXY
```

固定摄像头、固定手机时，第一层可用 4 个以上屏幕基准点拟合单应矩阵；第二层使用第二阶段得到的屏幕仿射映射。

生产校准的 `cameraPixel → screenPixel` 必须由屏幕平面绿色标靶生成。
绿靶未检出时应在不少于 3 秒的时间窗口内读取多幅新帧重试；仍失败则
本次拟合失败，不得静默退回到悬停探头尖像素。探头悬停平面与屏幕内容
平面不同，该退回会带入视差，不能用于 OCR/微信内容点击。

单应拟合除了检查重投影 RMS，还必须拒绝校准区域内存在投影极点、翻折
或发散的矩阵。仅因 RANSAC 选中 4 点而得到的 `RMS=0` 不能单独作为通过依据。

运行时识别任意内容后，统一执行：

```text
识别内容
→ 得到摄像头像素位置/区域
→ cameraPixel 转 screenPixel
→ screenPixel 转 robotXY
→ 回 hoverZ
→ XY 分段移动
→ TAP
```

## 9. 业务目标识别与点击语义

### 9.1 支持的内容类型

第一版支持：

1. 纯文字：点击文字框中心或用户指定的文字点击点。
2. 文字位于按钮中央：优先点击按钮安全中心。
3. 说明文字位于图标下方：将下方文字与最近的上方图标组合，点击图标中心。
4. 已登记的无文字图标：例如输入法删除图标、微信发送图标。
5. WX 业务所需的候选栏、输入区域、删除、发送、返回和会话入口。

第一版不支持未登记的任意纯图标。

### 9.2 目标选择优先级

```text
明确按钮区域
→ 文字所在按钮中心
→ 图标与下方名称组合中心
→ 指定文字中心
→ 已登记图标中心
→ 人工指定位置
```

存在多个同名文字、OCR 置信度过低或按钮关系不明确时，任务必须转人工确认，不允许猜测。

### 9.3 微信目标档案

至少登记以下目标：

```text
ime_candidate_bar
ime_delete_key
send_button
back_button
conversation_item
```

删除键应登记为支持长按的目标类型。发送按钮的登记和视觉识别不等于发送授权；
是否发送由 WX 决定，每次任务仍须核对账号、会话、批准正文哈希和执行证据，
不得以历史微信测试会话验收作为校准或发送门禁。

## 11. 运行前校准门禁

每个自动任务开始前执行 `validate_calibration_bundle()`，至少检查：

1. `status == ready`；
2. `daemonSession` 与 daemon 当前 session 相同；
3. 当前屏幕方向和尺寸与档案一致；
4. 当前摄像头画面能够检测到屏幕边缘；
5. 屏幕边缘偏差不超过 `tolerancePx`；
6. Z 参数完整且在安全范围；
7. XY 映射存在、可逆且残差合格；
8. 摄像头映射存在且重投影残差合格；
9. 当前任务所需目标已登记并通过验收；
10. 调试台输入法 E 的 `ime_input_tap`、`ime_delete_clear` 两项均通过；
11. 没有急停锁定、未知位置、过期租约或未确认的运动结果。

任何检查失败，自动任务统一返回：

```text
calibration_invalid
```

并附带具体原因，例如：

- `daemon_session_changed`；
- `screen_edge_changed`；
- `screen_orientation_changed`；
- `screen_size_changed`；
- `z_parameters_not_validated`；
- `xy_mapping_missing`；
- `camera_mapping_missing`；
- `target_not_validated`；
- `debug_acceptance_missing`。

上述门禁只证明当前设备具备执行已授权动作的校准条件，不授予微信发送许可。
历史 `wechat_acceptance_missing` 不再作为当前校准错误；WX 业务和发送证据检查独立执行。

### E. 调试台输入法验收

验收项目固定为两项：

1. `ime_input_tap`：下发一次固定文字，点击候选，确认文字进入输入区。
2. `ime_delete_clear`：点击或按已登记参数长按删除键，确认输入区清空。

自动 E 必须逐项等待：先执行第一项并保留输入结果供人工查看，只有人工确认通过后
才执行删除；删除结果同样由人工确认。两项均通过且其他门禁有效后，自动流程进入
`PROMOTE` 原子保存正式校准，不需要再点击手动完成按钮。取消、超时或未确认时不得继续删除或保存。

手动 E 由操作员逐项执行并确认，两项通过后使用“完成并保存校准”提交最终校验和保存。
这是手动完成入口的交互要求；按钮接线、部署及浏览器验证以本轮实际结果为准，
不因本文写明按钮名称就认定当前运行服务已更新。

生成验收报告、保存证据和完成档案是收尾操作，不增加验收项目。该区块不提供微信测试会话验收。

## 13. 当前校准验收顺序

手机固定后，全部校准及 E 验收在调试台与输入法页面完成：

1. 在输入法校准页完成 Z 参数验收。
2. 完成 XY 五点校准和额外验证点。
3. 完成视觉目标校准。
4. 执行 `ime_input_tap`：下发一次固定文字并点击候选，等待人工确认输入成功。
5. 第一项确认后才执行 `ime_delete_clear`：使用已登记删除键，等待人工确认输入区清空。
6. 保存两项证据并复核当前设备、摄像头、daemon 会话和其他校准门禁；自动流程全部通过后自动保存，手动流程通过“完成并保存校准”保存，才可将档案设为 `ready`。

历史说明：旧方案曾在调试台验收后要求进入测试微信，重复输入、发送、返回，
再用 `wechatAcceptance.send=true` 解锁发送。该流程已废止，不是当前 E 验收或
`ready` 的前置条件。真实微信业务验收由 WX 独立安排，不回写为机械臂校准要求。

## 14. 失败与恢复

### 点击没有回报

- 立即停止当前校准点；
- 不自动增加深度；
- 用户可重新调整 Z 参数或重新测试；
- 超时记录为 `touch_report_timeout`。

### 触点回报被拒绝

- 检查 session、sampleId、sequence；
- 检查输入法页是否仍为 open；
- 当前点不进入正式样本；
- 不允许用“最近一次未知触点”配对。

### 屏幕边缘变化

- 立即将校准档案标记为失效；
- 停止自动业务任务；
- 允许用户重新做屏幕几何和目标校准；
- 不直接复用旧目标的机械坐标。

### daemon session 变化

- Z、XY 和业务目标解析结果全部失效；
- 必须重新确认 `hoverZ`；
- 必须重新采集 XY 样本；
- 摄像头本身没有移动时，摄像头到屏幕的几何档案可以保留为参考，但统一档案仍不能标记 ready，直到 XY 验收完成。

### 微信发送失败或结果未知

- 不自动重试发送；
- 不继续下一个业务步骤；
- 保留屏幕现状和证据；
- 转人工处理。

## 15. 实施顺序

### Phase 1：统一档案和门禁

- 定义 `calibration_bundle.json`；
- 编写读写和版本校验；
- 接入 daemon session、屏幕尺寸、方向和屏幕边缘检查；
- 自动任务统一调用校准门禁。

### Phase 2：Z 校准向导

- 增加“标定 Z 轴高度”；
- 将普通点击和长按清除拆成两组参数；
- 扩展现有 `TAP P<sec>` 页面控件；
- 对接输入法触点回报；
- 增加保存和推荐 3 次成功记录。

### Phase 3：XY 五点向导

- 调试台创建输入法校准会话；
- 人工打开 K40 App 校准页；
- 系统分布 5 个目标；
- 用户点动修正并接受每个点；
- 拟合并记录残差；
- 增加 3 个独立验证点。

### Phase 4：屏幕边缘和视觉目标

- 固化屏幕边缘检测；
- 建立摄像头像素到屏幕像素的映射；
- 识别目标矩形、文字和图标下方名称；
- 支持用户修正并保存目标。

### Phase 5：调试台输入法 E 验收

- `ime_input_tap`：下发一次固定文字并点击候选，等待人工确认输入成功；
- 第一项确认通过后才执行 `ime_delete_clear`，再等待人工确认删除键清空；
- 保存两项执行和确认记录；其他目标测试属于其校准阶段，不增加 E 必选项。

### Phase 6：保存校准档案

- 复核当前设备、摄像头、daemon 会话及全部校准条件；
- 自动流程两项 E 验收逐项确认通过后自动原子保存正式档案和报告；
- 手动流程使用“完成并保存校准”执行最终校验和保存，不要求调用自动流程；
- 旧 `acceptance.wechat` 仅兼容读取，不触发测试微信，也不控制 `ready`。

## 16. 测试与验收标准

### 单元测试

- `TAP` 的深度、速度、停留参数编码正确；
- 普通点击和长按参数互不覆盖；
- 不共线检查；
- 仿射拟合和逆解；
- 摄像头单应拟合；
- 屏幕边缘偏差计算；
- 校准档案版本和 session 校验；
- 旧档案兼容读取。

### 协议测试

- 会话创建；
- 手机 `open/closed`；
- 布防；
- 合法触点回报；
- 乱序触点拒绝；
- 超时；
- 会话取消；
- 输入法长按验收事件。
- E 验收恰好为 `ime_input_tap`、`ime_delete_clear` 两项；
- 自动 E 第一项未人工确认时不得执行删除；第二项未确认时不得自动保存；
- 两项及其余门禁通过后自动保存，手动完成入口执行同等最终校验；
- 历史微信验收字段缺失或为假不阻断 `ready`，也不替代真实发送检查。

### 真机验收

- 普通点击至少一次稳定触发；
- 长按清除在可调时长下清空输入框；
- XY 五点拟合和独立点验证通过；
- 屏幕边缘未变化时页面内容改变不会导致误失效；
- 屏幕边缘发生变化时自动任务被拒绝；
- daemon 重连后自动任务被拒绝；
- 重新校准后任务恢复；
- 调试台内一次固定文字/候选点击和删除清空两项 E 验收通过；
- 不打开微信测试会话，也不执行微信发送来完成机械臂校准。

## 17. 当前结论

用户提出的流程可以落在现有架构上，关键运动能力已经存在：调试台的 `/api/tap`、daemon 的 `TAP ... P...` 和 K40 输入法的长按删除逻辑都可以复用。主要工作不是重写点击，而是把这些能力组织成统一状态机，保存成一个设备级校准档案，并在每次业务动作前执行屏幕边缘、session、参数和验收门禁。

第一版现场操作明确为：手机固定后，人工打开 K40 App 的“屏幕校准”，调试台负责后续会话、运动、触点监听、拟合、视觉校准及两项输入法 E 验收。本文说明流程，不证明当前设备已经校准或真实微信业务已经验收。
