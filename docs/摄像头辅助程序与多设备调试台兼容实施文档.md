## 1. 最终目标

最终链路固定为：

~~~
一台 CameraHelper.app
  -> 获取 macOS 摄像头权限
  -> 枚举 N 个 UVC 摄像头
  -> 按稳定 camera_id 管理每一路
  -> 上传各路 JPEG 帧

camera_frame_server.py
  -> 按 camera_id 隔离保存帧
  -> 提供分路状态和分路取帧

Arm Fleet / 电机调试台
  -> 用户选择 device_id
  -> 同时得到 camera_id、camera URL、daemon 地址和校准档案
  -> 校验完整设备上下文
  -> 完成该设备的校准和验收

业务运行
  -> 每次真实动作前检查校准门禁
  -> 通过才执行
  -> 不通过则拒绝自动任务
~~~

完成后必须保证：

1. arm-01 只能读取 cam-01 的画面。
2. arm-01 的运动只能发送给 arm-01 对应 daemon。
3. arm-01 的校准数据只能写入 arm-01 目录。
4. 切换到 arm-02 后，页面不得继续显示或使用 arm-01 的旧画面、旧连接或旧档案。
5. 任意摄像头、机械臂、daemon、帧身份或校准档案不匹配时，禁止运动、点击、采样、拟合和保存完成状态。
6. 更换 Chrome 取流方式不得重写现有画质检测、OCR、运动验证和校准数学逻辑。

## 3. 已冻结的实现决定

### 3.1 单一辅助程序

用户要求的“单一文件”固定解释为：

> 现场只启动一个 CameraHelper.app，由它同时管理所有摄像头；不得为每个摄像头启动一个独立 App、脚本或 Chrome 页面。

CameraHelper.app 可以由多个源码文件组成，但交付和启动单位只能有一个。

### 3.2 正式取流方向

正式链路固定为：

~~~
CameraHelper.app 采集
  -> HTTP POST JPEG
  -> camera_frame_server.py 保存
  -> Arm Fleet 和调试台 HTTP GET
~~~

禁止 Arm Fleet、调试台、WX 分别直接打开同一 UVC 摄像头。

### 3.3 摄像头编号

第一版预置：

~~~
cam-01
cam-02
...
cam-10
~~~

内部实现必须使用以 camera_id 为键的集合，不得使用十套复制代码，因此以后增加 cam-11 不需要修改核心逻辑。

### 3.4 稳定物理身份

物理摄像头身份必须使用 AVFoundation 返回的 device_unique_id。

camera_index 只能用于：

- 当次设备枚举排序；
- 界面展示；
- 首次人工选择。

camera_index 禁止用于服务重启后的自动绑定。

### 3.5 唯一校准档案

每台设备只有一份自动任务校准事实源：

~~~
data/devices/{device_id}/calibration_bundle.json
~~~

以下旧文件只能迁移或诊断，禁止参与自动任务最终门禁：

~~~
data/motor_debug_calibration.json
data/screen_ime_mappings.json
data/devices/{device_id}/calibration.json
data/devices/{device_id}/targets.json
configs/screen_calibration.json
~~~

### 3.6 重启不等于重新校准

CameraHelper、帧接收服务或 Arm Fleet 单纯重启，不直接使摄像头几何校准失效。

重启后必须重新检查：

1. camera_id 一致；
2. device_unique_id 一致；
3. 画面宽高一致；
4. 屏幕方向一致；
5. 屏幕四角最大偏差不超过 8px；
6. 帧序号持续增长；
7. 帧年龄不超过 1500ms。

七项全部通过时，摄像头与屏幕几何映射继续有效。

daemon session 改变属于机械坐标系变化。发生后 Z 和 XY 必须重新确认，整体档案不得继续为 ready。

### 3.7 旧单路接口

旧 /latest.jpg 只允许 arm-01 单台兼容使用。

当两路或以上摄像头同时推流时，旧 /latest.jpg 必须返回 HTTP 409，禁止自动返回“最近上传的一路”。

## 5. 唯一标识和事实源

### 5.1 标识

| 字段 | 格式 | 示例 | 来源 |
|---|---|---|---|
| device_id | arm-NN | arm-01 | configs/devices.json |
| camera_id | cam-NN | cam-01 | configs/devices.json |
| device_unique_id | AVFoundation 原始值 | 系统字符串 | macOS |
| daemon_addr | host:port | 127.0.0.1:8795 | configs/devices.json |
| daemon_session | UUID 类字符串 | session-id | daemon |
| context_id | ctx-UUID | ctx-... | 调试台后端 |
| binding_revision | 正整数 | 7 | 帧接收服务 |

### 5.2 三个事实源

只允许：

1. configs/devices.json：device、camera 和 daemon 的逻辑绑定。
2. data/camera_helper/bindings.json：camera_id 和物理 device_unique_id 的绑定。
3. data/devices/{device_id}/calibration_bundle.json：校准与验收。

三者关系固定为：

~~~
devices.json
  arm-01 -> cam-01 -> 127.0.0.1:8795

bindings.json
  cam-01 -> avfoundation-unique-id-01

calibration_bundle.json
  保存上述组合完成的 Z、XY、camera 和验收结果
~~~

### 5.3 绑定指纹

运行时必须计算：

~~~
SHA-256(
  device_id + 换行 +
  camera_id + 换行 +
  device_unique_id + 换行 +
  daemon_addr + 换行 +
  frame_width + "x" + frame_height
)
~~~

结果保存为 bindingFingerprint。当前指纹与档案不一致时，运行门禁失败。

### 5.4 启动时必须拒绝

- 重复 device_id；
- 两个设备使用同一个 camera_id；
- 两个真实设备使用同一个 daemon_addr；
- 两个 camera_id 绑定同一个 device_unique_id；
- real 设备缺少 camera_id；
- real 设备缺少 daemon_addr；
- multi_channel URL 不包含本设备 camera_id；
- simulation 设备指向真实 daemon 或真实摄像头。

## 6. 设备配置规范

真机设备必须具备：

~~~json
{
  "device_id": "arm-01",
  "name_display": "设备 arm-01（真机）",
  "arm_slot": 1,
  "driver_mode": "daemon",
  "binding_mode": "real",
  "camera_id": "cam-01",
  "camera_mode": "multi_channel",
  "camera_frame_url": "http://127.0.0.1:8790/cameras/cam-01/latest.jpg",
  "camera_status_url": "http://127.0.0.1:8790/cameras/cam-01/status",
  "expected_frame_width": 1280,
  "expected_frame_height": 720,
  "expected_frame_fps": 10,
  "daemon_addr": "127.0.0.1:8795",
  "wechat_account_id": "pending-real-acc-01"
}
~~~

规则：

1. binding_mode=real 时以上字段全部必填。
2. camera_mode=multi_channel 时必须使用分路 URL。
3. camera_mode=legacy_single 只允许 arm-01。
4. legacy_single 的 frame URL 固定为 http://127.0.0.1:8790/latest.jpg。
5. daemon 端口不由公式推算，以配置值为准。
6. 前端不得传入任意 camera URL 或 daemon 地址。
7. 服务端只能从已加载配置解析真实地址。

## 7. CameraHelper.app 规范

### 7.1 摄像头权限

Info.plist 必须包含：

~~~
NSCameraUsageDescription =
用于采集固定安装的手机屏幕摄像头画面，供机械臂校准和运行检查使用。
~~~

启动顺序固定为：

1. 查询摄像头授权状态。
2. notDetermined 时请求系统授权。
3. denied 或 restricted 时停止枚举和推流。
4. authorized 时枚举视频设备。
5. 没有设备时显示“未发现摄像头”，禁用启动按钮。

### 7.2 主界面

必须显示一个通道表格，每行包含：

- camera_id；
- 物理摄像头名称；
- device_unique_id 后 8 位；
- 实际宽高；
- 实际帧率；
- 上传状态；
- 最近上传成功时间；
- 启动或停止按钮。

必须提供：

- 刷新设备；
- 保存绑定；
- 启动所选；
- 停止所选；
- 启动全部已绑定通道；
- 停止全部。

### 7.3 绑定流程

固定步骤：

1. 用户选择 camera_id。
2. 用户选择物理摄像头。
3. App 显示完整 device_unique_id 和实时预览。
4. 用户点击保存绑定。
5. App 调用 PUT /cameras/{camera_id}/binding。
6. 服务检查重复绑定和逻辑配置。
7. 服务保存并返回新的 bindingRevision。
8. App 刷新状态。

正在推流的 camera 不允许直接换绑，必须先停止。

### 7.4 固定采集参数

第一版固定值：

~~~
目标宽度：1280
目标高度：720
目标帧率：10 fps
JPEG quality：0.85
单帧最大值：8 MiB
上传超时：2 秒
失败重试间隔：1 秒
~~~

如果实际宽高与设备配置不同：

- 可以显示诊断预览；
- 通道状态必须为 resolution_mismatch；
- 禁止调试台采样、拟合和点击。

### 7.5 并发

每个 camera_id 必须有独立：

- AVCaptureSession；
- 输入设备；
- JPEG 编码队列；
- 上传队列；
- 帧计数；
- 错误状态。

某一路掉线不能停止其他路。

每路上传队列只保留最新待上传帧。网络慢时丢弃旧待上传帧，禁止无限排队。

### 7.6 重启恢复

App 重启后：

1. 重新检查权限；
2. 重新枚举；
3. 按 device_unique_id 恢复绑定；
4. 缺失摄像头标记 unavailable；
5. 禁止自动把同名新设备替换进旧 camera_id；
6. autoStart 第一版默认 false。

## 8. 帧接收服务接口

服务固定监听：

~~~
127.0.0.1:8790
~~~

禁止监听 0.0.0.0。

### 8.1 通用错误

~~~json
{
  "ok": false,
  "error": {
    "code": "camera_binding_mismatch",
    "message": "摄像头绑定不一致",
    "details": {}
  }
}
~~~

客户端按 code 判断，不得解析中文决定逻辑。

### 8.2 健康检查

~~~
GET /health
~~~

返回 serviceVersion 和 bindingRevision。

### 8.3 摄像头列表

~~~
GET /cameras
~~~

每路必须返回：

- cameraId；
- deviceId；
- deviceUniqueId；
- displayName；
- bindingRevision；
- status；
- hasFrame；
- frameSeq；
- capturedAt；
- receivedAt；
- ageMs；
- width；
- height；
- lastError。

### 8.4 保存绑定

~~~
PUT /cameras/{camera_id}/binding
Content-Type: application/json
~~~

~~~json
{
  "deviceUniqueId": "avfoundation-unique-id-01",
  "displayName": "UVC Camera",
  "operator": "local-operator"
}
~~~

处理规则：

| 条件 | HTTP | code |
|---|---:|---|
| camera_id 不存在 | 404 | camera_not_found |
| 已存在相同物理绑定且通道正在推流 | 200 | binding_unchanged=true，不改变 revision 或帧 |
| 通道正在推流且请求改绑到其他物理摄像头 | 409 | camera_still_streaming |
| unique id 已被其他 camera 使用 | 409 | camera_unique_id_conflict |
| 保存成功 | 200 | 无错误 |

绑定保存到 data/camera_helper/bindings.json，并原子替换。每次变更 revision 加一。
重复提交同一 `camera_id + deviceUniqueId` 是幂等操作，不增加 revision；只有实际绑定变化才增加 revision。

### 8.5 删除绑定

~~~
DELETE /cameras/{camera_id}/binding
~~~

正在推流时返回 409。删除后必须立即清空该通道历史帧。

### 8.6 正式上传

~~~
POST /cameras/{camera_id}/frame
Content-Type: image/jpeg
X-Camera-Id: cam-01
X-Camera-Unique-Id: avfoundation-unique-id-01
X-Captured-At: 2026-09-01T20:00:00.100+08:00
X-Source-Frame-Seq: 551
~~~

必须按顺序检查：

1. path camera_id 合法；
2. X-Camera-Id 存在且等于 path；
3. X-Camera-Unique-Id 等于保存绑定；
4. Content-Type 正确；
5. body 大于 0 且不超过 8 MiB；
6. JPEG 可以解码；
7. 宽高可以读取；
8. 服务端生成新的 frameSeq；
9. 记录 capturedAt 和 receivedAt；
10. 原子替换该通道最新帧。

服务端 frameSeq 是冻结判断的唯一序号。X-Source-Frame-Seq 只用于诊断。

### 8.7 状态

~~~
GET /cameras/{camera_id}/status
~~~

状态固定为：

| 状态 | 条件 |
|---|---|
| unbound | 没有物理绑定 |
| configured | 已绑定但从未收到合法帧 |
| streaming | ageMs 小于等于 1500 |
| stale | 1500 小于 ageMs 小于等于 10000 |
| unavailable | ageMs 大于 10000 或采集停止 |
| wrong_binding | 最近上传身份冲突 |
| resolution_mismatch | 实际宽高与配置不一致 |

wrong_binding 和 resolution_mismatch 优先于时间状态。

### 8.8 分路图片

~~~
GET /cameras/{camera_id}/latest.jpg
~~~

只有 streaming 返回 200。必须带：

~~~
X-Camera-Id
X-Device-Id
X-Camera-Unique-Id
X-Binding-Revision
X-Frame-Seq
X-Captured-At
X-Received-At
X-Frame-Width
X-Frame-Height
~~~

非 streaming 不得返回历史帧冒充实时帧：

- 未知或未绑定：404；
- 绑定或分辨率错误：409；
- 无帧、stale、unavailable：503。

### 8.9 Chrome 兼容

保留：

~~~
GET /latest.jpg
GET /status
POST /frame
~~~

规则：

1. 启动参数 --legacy-camera-id cam-01 才启用。
2. 未启用时返回 410 legacy_mode_disabled。
3. 两路或以上 streaming 时 /latest.jpg 返回 409。
4. 多设备正式配置禁止使用兼容接口。
5. Chrome 页面只作为 CameraHelper 故障时 arm-01 单台回滚方案。

## 9. Arm Fleet 接入

### 9.1 HttpFrameSource

构造参数固定增加：

~~~python
HttpFrameSource(
    url,
    expected_camera_id,
    expected_device_id,
    expected_device_unique_id,
    expected_width,
    expected_height,
    allow_legacy=False,
    timeout=3.0,
)
~~~

每次取帧必须检查：

1. HTTP 200；
2. JPEG 可解码；
3. camera id 正确；
4. device id 正确；
5. physical unique id 正确；
6. binding revision 可解析；
7. frame seq 可解析且不倒退；
8. receivedAt 可解析；
9. 帧年龄不超过 1500ms；
10. 响应头宽高等于 JPEG 实际宽高；
11. 实际宽高等于设备配置。

allow_legacy=true 只允许身份头缺失，不允许过期帧、错误 JPEG 或错误分辨率。该值只允许 arm-01。

对象必须保存最近一次来源元数据，供 RealCameraDriver、证据和门禁使用。

### 9.2 RealCameraDriver

capture_sync 返回结果必须增加：

- camera_id；
- device_id；
- device_unique_id；
- binding_revision；
- source_frame_seq；
- source_received_at；
- source_legacy_mode。

现有画质分类、参考图匹配和运动帧差逻辑继续使用，不重写。

### 9.3 DeviceManager

固定规则：

1. real + multi_channel 必须使用 camera_frame_url。
2. real + legacy_single 只允许 arm-01。
3. real 缺字段时设备注册失败。
4. simulation 继续使用仿真驱动。
5. 每个设备只创建一个 HttpFrameSource。
6. 查看、监听、质量巡检和运动验证共享该设备 CameraFrameBroker。
7. 多设备正式模式禁止回退全局 /latest.jpg。

## 12. 调试台页面

### 12.1 页面状态机

固定为：

~~~
NO_DEVICE
  -> LOADING_CONTEXT
  -> READY
  -> SWITCHING
  -> LOADING_CONTEXT

~~~

| 状态 | 画面 | 运动 | 校准 |
|---|---|---|---|

| LOADING_CONTEXT | 清空 | 禁用 | 禁用 |
| READY | 当前设备分路画面 | 按状态启用 | 按阶段启用 |
| SWITCHING | 立即清空旧画面 | 禁用 | 禁用 |

### 12.2 常驻显示

必须显示：

- 当前机械臂；
- 当前摄像头；
- 物理摄像头名称和唯一标识后 8 位；
- 分辨率、帧率、帧年龄；
- daemon deviceId、地址和 session；
- binding revision；
- 校准档案路径；
- 校准状态。

只显示机械臂编号不合格。

### 12.3 切换顺序

arm-01 切换 arm-02 时：

1. 进入 SWITCHING；
2. 禁用全部按钮；
3. 停止旧画面和状态轮询；
4. 清空 img src；
5. 取消旧网络请求；
6. 删除旧 context；
7. 创建 arm-02 context；
8. 显示 arm-02 绑定；
9. 启动 arm-02 轮询；
10. 启动 arm-02 画面；
11. 加载 arm-02 向导和档案；
12. 全部成功后进入 READY。

任一步失败进入 BLOCKED，不得恢复旧按钮状态。

### 12.4 防止旧响应污染

前端必须维护 selectionGeneration。每次设备切换加一。

真正的运动安全由后端 contextId 校验负责，不能只依赖前端。

## 13. 逐台校准流程

必须按顺序完成，禁止跳阶段写 ready。

### 13.1 前置条件

1. 当前设备上下文 READY；
2. 手机已人工固定；
3. 摄像头已固定；
4. camera identity、分辨率和帧年龄通过；
5. daemon identity 和 session 通过；
6. 急停未锁定；
7. 调试台取得 debug 租约；
8. 手机已安装 K40 输入法；
9. 用户已人工打开 K40 App 的屏幕校准页；
10. 输入法校准会话 clientState=open。

### 13.2 Z 悬停高度

1. 用户点动 Z 到不接触屏幕的位置。
2. 点击“标定 Z 轴高度”。
3. 后端读取当前 MPos.z。
4. 保存为 hoverZ。
5. 同时保存 device、camera、frameSeq、daemonSession 和时间。
6. 页面显示保存结果。

daemon session 改变后必须重新确认 hoverZ。

### 13.3 普通点击

用户可调：

~~~
tapDepth：0 < value <= 10mm
tapFeed：30 <= value <= 2000 mm/min
tapDwellMs：0 <= value <= 2000ms
~~~

回升不单独设置速度，固定使用 tapFeed。

测试步骤：

1. 输入法服务布防 sampleId 和 sequence。
2. 执行 TAP depth Ffeed P(dwellMs/1000)。
3. TAP 自动回到点击前 Z。
4. 页面等待匹配触点回报。
5. 合法回报到达后显示参数和坐标。
6. 用户选择“合理并保存”或“继续调整”。

保存硬条件：

- 至少一次合法触点回报；
- 用户明确点击“合理并保存”。

连续三次成功只显示为建议值，不阻止保存，不作为 ready 硬门槛。

### 13.4 长按清除

独立参数：

~~~
deleteDepth
deleteFeed
deleteHoldMs：800 到 5000ms
初始值：2200ms
~~~

验收：

1. 输入法测试区有文字；
2. 机械臂移动到已登记删除键；
3. 执行长按；
4. 输入法回报清空；
5. 用户确认输入区为空；
6. 保存独立长按参数。

普通点击和长按参数禁止互相覆盖。

### 13.5 XY 机械与屏幕

正式样本至少 5 个，固定分布：

- 中心；
- 左上安全区；
- 右上安全区；
- 左下安全区；
- 右下安全区。

每点：

1. 手机显示目标；
2. 用户通过摄像头观察；
3. 用户点动 XY 修正；
4. 点击准备本点；
5. 记录 robot X/Y 和 frame identity；
6. 布防触点；
7. 执行 TAP；
8. 输入法回报根视图 MotionEvent.x/y；
9. 用户接受或拒绝；
10. 只有接受点进入拟合。

拟合：

~~~
screenX = a*robotX + b*robotY + c
screenY = d*robotX + e*robotY + f
~~~

通过条件：

- accepted 点不少于 5；
- robot 点不共线；
- 屏幕方向和尺寸一致；
- RMS 小于等于 3px；
- 单点最大残差小于等于 6px；
- 矩阵可逆。

拟合后必须使用 3 个不参与拟合的验证点：

- 每点误差小于等于 6px；
- 三点 RMS 小于等于 3px。

### 13.6 摄像头与屏幕

建立：

~~~
cameraPixel -> screenPixel
~~~

手机校准页依次显示 5 个绿色目标：

- 左上；
- 右上；
- 中心；
- 左下；
- 右下。

每点在 3 秒内读取多幅新帧并检测绿色目标。使用有效点拟合单应矩阵。

通过条件：

- 至少 5 个有效目标；
- 重投影 RMS 小于等于 3px；
- 单点最大误差小于等于 6px；
- 矩阵不存在极点、翻折或发散。

绿色目标检测失败时本点失败。禁止使用悬停探头尖代替屏幕平面绿色目标。

### 13.7 目标语义

第一版支持：

1. 纯文字：点击文字区域中心。
2. 文字位于按钮内：点击按钮安全中心。
3. 文字位于图标下方：将文字和最近的上方图标组合，点击图标中心。
4. 已登记无文字图标：使用保存区域，例如删除键和发送按钮。

未登记、无文字的任意图标返回 unsupported_unregistered_icon，转人工。

完整点击链路：

~~~
目标 camera pixel
  -> cameraToScreen
  -> screen pixel
  -> robotToScreen 逆变换
  -> robot XY
  -> hoverZ
  -> 分段移动
  -> TAP
~~~

### 13.8 调试台验收

E 验收固定只有两项：

1. `ime_input_tap`：输入法下发一次固定文字并点击候选，确认输入成功。
2. `ime_delete_clear`：点击已登记删除键并确认输入区清空。

自动 E 先执行第一项，等待人工确认通过后才执行删除；第二项也须人工确认。
两项及其他校准门禁全部通过后自动原子保存正式档案，不再等待手动完成按钮。
手动 E 则逐项执行/确认后，通过“完成并保存校准”完成最终校验与保存；
该手动入口的接线和运行服务部署以实际验证结果为准。取消、超时或未确认不得自动继续下一项。

不是两次文字输入，也不进入微信测试会话。摄像头持续更新和 device、camera、daemon 身份一致
是两项验收共同的运行前提，不是额外的 E 项目。真实 WX 发送不由调试台验收代替；每次发送仍由 WX
运行时校验目标、正文哈希和执行证据。

### 13.9 `acceptance.wechat` 历史兼容记录

旧版测试微信会话流程仅用于读取或迁移历史 `acceptance.wechat` 记录，不是当前校准前置，不控制
`calibration_bundle.status=ready`，也不构成真实发送门禁。当前 E 阶段按上一节完成两项输入法
验收并保存证据；证据保存不是第三项验收。

WX 每次真实发送仍由 WX 运行时独立校验目标、正文哈希和执行证据；不得用
`acceptance.wechat` 或本节调试台记录替代这些运行时检查。

当前校准各阶段和两项调试台 E 验收全部通过后，calibration_bundle.status 才能为 ready，
不等待历史微信验收字段。

## 15. 失效规则

### 15.1 必须失效

- device_id 变化；
- camera_id 变化；
- device_unique_id 变化；
- daemon_addr 变化；
- binding fingerprint 变化；
- daemon session 变化；
- 摄像头位置变化；
- 手机位置变化导致屏幕四角最大偏差大于 8px；
- 画面宽高变化；
- 屏幕方向或有效尺寸变化；
- XY 或 camera 矩阵损坏、不可逆或超阈值；
- 档案版本不支持；
- 点击参数被修改但未重新验收。

### 15.2 不因事件本身失效

- CameraHelper 重启；
- frame server 重启；
- Arm Fleet 重启；
- 微信页面文本变化；
- 客户名称变化；
- 输入框文字变化；
- 允许范围内的亮度变化。

服务重启后仍必须重新执行现场检查。检查失败时按具体原因失效。

### 15.3 分层处理

daemon session 变化：

- Z 失效；
- XY 失效；
- robot 落点失效；
- cameraToScreen 可保留为参考；
- 整体不得 ready。

屏幕边缘变化：

- cameraToScreen 失效；
- XY 必须重新验证；
- 目标落点失效；
- Z 参数可保留为待验证；
- 整体不得 ready。

## 16. 运行前门禁

每个真实运动、点击或发送前必须按顺序检查：

1. 设备存在且为 real；
2. 设备未隔离；
3. 急停未锁定；
4. 任务持有合法运动租约；
5. camera 状态为 streaming；
6. frame age 小于等于 1500ms；
7. camera、device、unique id、binding revision 匹配；
8. 分辨率匹配；
9. daemon deviceId 匹配；
10. daemon session 匹配；
11. bundle schema 支持；
12. bundle status 为 ready；
13. binding fingerprint 匹配；
14. 屏幕方向和尺寸匹配；
15. 屏幕四角最大偏差小于等于 8px；
16. Z、XY、camera 均 validated；
17. 当前目标已支持并验收；
18. 调试台输入法 E 验收通过（固定文字输入、候选点击和删除键清空）；
19. 上一动作不存在 result unknown。

任一失败统一返回 calibration_invalid，并带具体 reasonCode。

禁止自动：

- 绕过门禁；
- 增加点击深度；
- 更换摄像头；
- 更换 daemon；
- 重试微信发送。

## 25. 现场执行清单和唯一判定

本节把前述规范转换成现场唯一操作顺序。现场人员不得跳步，不得把“能看到画面”“机械臂能动”或“偶尔点击成功”视为校准完成。

### 25.1 启动前准备

每台真实设备必须提前确定以下四项，缺少任一项不得启动校准：

| 项目 | arm-01 示例 | 判定规则 |
|---|---|---|
| 机械臂 | `arm-01` | `configs/devices.json` 中唯一 |
| 摄像头通道 | `cam-01` | 不与其他设备重复 |
| 物理摄像头 | AVFoundation unique ID | 不与其他通道重复 |
| daemon | `127.0.0.1:8795` | 不与其他真实设备重复 |

手机必须已经固定在最终工作位置，摄像头必须已经固定在最终工作位置。校准开始后，禁止移动手机支架、摄像头、机械臂底座或改变手机屏幕方向。

### 25.2 固定启动顺序

必须按以下顺序启动：

1. 启动 `camera_frame_server.py`，正式模式不得开启旧全局帧接口。
2. 打开 `CameraHelper.app`，确认 macOS 摄像头权限为已允许。
3. 在 `cam-NN` 通道选择指定物理摄像头并保存绑定。
4. 启动该通道，确认状态为 `streaming`，帧序号增长，帧年龄不超过 1500ms，分辨率为 1280×720。
5. 使用该设备的 `device_id` 启动对应 daemon，并确认 daemon 返回相同 `deviceId`。
6. 启动 Arm Fleet 和调试台。
7. 在调试台选择目标机械臂，等待后端返回新的 `context_id`。
8. 核对页面常驻显示的 `device_id`、`camera_id`、物理摄像头身份、daemon 地址和校准档案路径。
9. 五项完全一致后，才允许进入校准。

任一步失败时，页面必须进入阻断状态。用户只能修复当前绑定或服务后重新建立 context，禁止沿用旧 context 继续操作。

### 25.3 单台设备校准顺序

每台设备必须独立执行，顺序固定如下：

1. **Z 悬停高度**：人工点动 Z 轴，使触点位于安全悬停高度；点击“标定 Z 轴高度”。保存的是当前绝对 Z 位置，不是下压距离。
2. **普通点击参数**：设置下压速度、停留时间和下压行程；点击“测试点击”；调试台开始监听输入法点击回报。输入法回报到达后由用户判断触发是否合理。用户确认合理并点击“保存点击参数”后，该组参数才生效。未收到回报或用户未确认时禁止保存为通过。
3. **长按清除参数**：设置长按动作时间，执行输入法“删除全部内容”测试。必须确认长按能够清空全部输入内容，才允许保存。长按时间是独立参数，不得直接等同于普通点击停留时间。
4. **XY 机械映射**：Z 和普通点击均已通过后，用户通过摄像头把触点移动到屏幕中部；点击“开始校准 XY”。机械臂先点击基准点，再向系统选择的安全短距离方向移动并点击第二点。两次输入法回报必须有效，系统据此建立机械坐标与屏幕坐标关系。用户确认落点后保存 XY。
5. **摄像头与屏幕映射**：输入法打开其内置校准页面。系统显示可点击目标，机械臂按摄像头识别结果点击。至少完成 5 个分布在屏幕不同区域的有效目标；目标不得全部集中在同一区域。用户逐点确认实际落点并修正，系统拟合摄像头像素与屏幕内容坐标关系。
6. **调试台输入法 E 验收**：下发一次固定文字并点击候选，等待人工确认输入成功后才执行删除，随后等待人工确认清空。保存两项证据；不要求微信测试会话。
7. **保存档案**：前述校准和两项 E 验收全部通过后，自动流程自动保存；手动流程使用“完成并保存校准”。最终将 `data/devices/{device_id}/calibration_bundle.json` 保存为 `ready`，同时写入设备、摄像头、物理摄像头、daemon、分辨率和绑定指纹。历史 `acceptance.wechat` 不参与放行。

### 25.4 多设备增加顺序

增加第二台及后续设备时，必须完整完成当前设备后再接入下一台：

~~~text
arm-01 绑定 -> arm-01 校准 -> arm-01 调试台 E 验收 -> arm-01 ready
arm-02 绑定 -> arm-02 校准 -> arm-02 调试台 E 验收 -> arm-02 ready
~~~

禁止复制其他设备的 `calibration_bundle.json`。即使机械臂、手机和摄像头型号相同，也必须逐台重新校准。

### 25.5 运行前唯一放行条件

自动任务开始前以及每次真实移动或点击前，以下条件必须同时成立：

1. 目标设备启用且状态正常；
2. 当前 context 未过期且属于目标设备；
3. camera_id 与设备配置一致；
4. 物理摄像头 unique ID 与保存档案一致；
5. binding revision 与当前绑定一致；
6. 画面宽高与校准时一致；
7. 屏幕方向一致；
8. 屏幕四角最大偏差不超过 8px；
9. 最新帧年龄不超过 1500ms；
10. 帧序号持续增长；
11. daemon 地址、deviceId 和 session 与当前档案一致；
12. Z、普通点击、长按、XY、视觉和调试台输入法 E 验收均为通过；
13. `bindingFingerprint` 重新计算后与档案一致；
14. 校准档案状态为 `ready`。

任一条件不成立，结果只有一种：拒绝自动任务和真实动作，并返回第 17 节规定的明确错误码。禁止降级为猜测设备、复用旧帧、使用旧 context、读取全局 `/latest.jpg` 或绕过校准门禁。

### 25.6 变化后的处理

| 变化 | 处理结果 | 恢复方式 |
|---|---|---|
| 仅重启 CameraHelper、帧服务或 Arm Fleet | 不自动失效 | 七项摄像头检查通过后继续使用 |
| CameraHelper 暂时断流 | 暂停该设备 | 恢复同一物理摄像头且检查通过 |
| 更换物理摄像头 | 视觉校准失效 | 重新完成摄像头与屏幕映射及后续验收 |
| 分辨率变化 | 视觉校准失效 | 恢复原分辨率或重新完成视觉校准 |
| 屏幕方向变化 | 视觉校准失效 | 恢复原方向或重新完成视觉校准 |
| 屏幕边缘偏差大于 8px | 视觉校准失效 | 固定手机后重新完成视觉校准 |
| daemon session 变化 | Z、XY 和整体验收失效 | 重新确认 Z、点击、XY 和后续验收 |
| 修改下压速度、停留时间或行程 | 点击验收失效 | 重新测试并保存普通点击参数 |
| 修改长按时间 | 长按验收失效 | 重新执行清空测试并保存 |
| 仅微信页面内容变化 | 不因此失效 | 运行时识别并点击已支持目标 |
| 移动手机、摄像头或机械臂底座 | 整体失效 | 从对应设备的 Z 步骤重新校准 |

### 25.7 最终验收结论用语

验收报告只能使用以下三种结论：

1. `软件实现完成`：代码、专项测试、全量回归和构建已完成，但没有真实双设备证据。

3. `多设备真机验收完成`：至少两套真实设备同时在线，逐台校准和调试台 E 验收通过，并完成摄像头、daemon、context 和档案串线阻断测试。
